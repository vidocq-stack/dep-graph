# `graph/` — the reverse dependency graph

This directory holds the aggregated Vidocq dependency graph.

## `inverted.json`

Generated by `scripts/build_inverted_graph.py` from `data/*.json`. Never edit it by hand:
`scripts/update_data_file.sh` rebuilds it in the same commit as every data update, and
`.forgejo/workflows/build-graph.yml` rebuilds it after any other commit that touches `data/**` or
the builder.

Format:

```json
{
  "schema_version": 1,
  "generated_at": "2026-10-25T14:38:46Z",
  "artifacts": {
    "io.vidocq.vauban:vauban-core": {
      "produced_by": "Vidocq/vauban",
      "consumed_by": [
        {"repo": "Vidocq/cassini", "scope": "compile"},
        {"repo": "Vidocq/foy",     "scope": "compile"},
        {"repo": "Vidocq/mansart", "scope": "test"}
      ]
    }
  }
}
```

- Key: `groupId:artifactId` (no version).
- `produced_by`: the repository that publishes the artifact.
- `consumed_by`: the consumer repositories, with the Maven `scope` (`compile`, `runtime`,
  `provided`, `test`, `import`, or `build` for plugins, plugin dependencies and annotation
  processor paths).
- Lists are sorted by `(repo, scope)` so that diffs stay stable.
- `generated_at` is compared with the producer data's `updated_at` by the CI: a graph older than
  the producer's data file fails the downstream resolution (it may miss consumers).

## Rules

- Only the data files whose `repo` field belongs to the `Vidocq` organisation are indexed (the
  owner is compared case-insensitively, see `scripts/build_inverted_graph.py`).
- When two repositories declare the same artifact as produced, the first one read wins and the
  builder prints a warning on stderr (a pathological case).
- Repository-to-repository cycles are detected and reported on stderr, without failing the build.
- `build_inverted_graph.py --check` writes nothing and exits 1 when there is at least one warning.

## How to query it

The consumers impacted by a change of a producer:

```bash
python3 scripts/resolve_impact.py \
  --graph graph/inverted.json \
  --changed io.vidocq.vauban:vauban-core io.vidocq.vauban:vauban-api \
  --format matrix
```

Output:

```json
{"include": [{"repo": "Vidocq/cassini"}, {"repo": "Vidocq/foy"}, {"repo": "Vidocq/mansart"}, {"repo": "Vidocq/vidocq"}]}
```

`--depth N` stops at N levels (`all`, the default, is the full transitive closure). `--ordered`
sorts the result in topological order, producer before consumer.

The CI calls it with `--ordered` on every artifact of the producer
(`Vidocq/ci/build-impacted/resolve-consumers.sh`), then keeps the repositories that exist on the
forge:

- `Vidocq/ci/resolve-impacted` turns the list into the job matrix of the pull request's
  `downstream` jobs, one `build-one-consumer` job per consumer, run in parallel;
- `Vidocq/ci/build-impacted` rebuilds the consumers one after the other, in that order, for the
  nightly chain of the producers with at least five transitive consumers.
